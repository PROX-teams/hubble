# 노트 작성·발행 흐름

- 새 글은 임시저장 없이 바로 게시할 수 있다.
- 초안 저장 요청의 `noteId`가 null이면 새 글, 값이 있으면 해당 게시글의 수정 초안이다. 수정 대상은 작성자 소유인지 서버에서 검증한다.
- 게시/수정 요청은 에디터의 최신 내용과 선택적 `draftId`를 전달한다. 서버는 초안 소유권과 수정 대상의 일치 여부를 검사한다.
- 노트·태그 갱신과 초안의 `published=true`, `noteId` 설정은 같은 트랜잭션에서 수행한다. 실패하면 함께 롤백된다.
- 발행 완료 초안은 임시저장 목록에서 제외한다. 재시도 판별과 늦은 저장 요청 차단을 위해 DB 레코드는 보존한다. 임시저장 삭제/전체 삭제도 발행 완료 레코드를 제거하지 않는다.
- 같은 초안을 다시 발행하면 이미 연결된 게시글을 반환한다. 완료된 초안 저장이나 존재하지 않는 초안의 저장은 거절한다.
- 수정 초안을 저장하는 동안 공개 노트는 변경하지 않는다. 수정 완료 시 기존 노트를 갱신한다. 목록에서 수정 초안을 선택하면 해당 노트의 수정 화면으로 이동한다.
- 프론트는 수동·자동 저장 요청을 순차 처리하고, 발행 시 진행 중인 저장을 기다린다. 발행 중에는 새 저장을 차단한다.

## 적용 및 검증 범위

백엔드와 프론트를 함께 반영해야 한다. Flyway V7 마이그레이션은 `drafts.note_id`, `drafts.published`를 추가한다. 기존 초안은 새 글 초안으로 유지되며, 과거 게시글과의 연결을 추측해서 만들지 않는다.

서비스 단위 테스트와 TypeScript 검사로 검증한다. 실제 MySQL의 트랜잭션 롤백, 잠금 경쟁, 브라우저 동작은 별도의 통합 검증이 필요하다.

초안 없이 게시하는 요청의 재시도 멱등성, 게시글 자체의 버전 충돌 감지는 이 변경에 포함하지 않는다. 동일 게시글의 여러 수정 초안은 허용한다. 발행 완료 초안 보존 기간과 정리 정책은 별도로 결정해야 한다.

## 초안 버전 검사

Flyway V8은 초안에 `version BIGINT NOT NULL DEFAULT 0`을 추가한다. `@Version`으로 DB 갱신 시 충돌을 검사하고, 응답에 실제 반영된 버전을 반환하기 위해 저장 후 flush한다. 기존 초안 저장 요청에는 조회 시 받은 버전이 필수이며, 누락 또는 불일치는 HTTP 409로 응답한다. 동시에 같은 버전을 저장하는 요청은 JPA 낙관적 락으로 충돌을 감지한다.

프론트는 목록에서 초안을 열 때 버전도 복원하고, 저장 성공 시 반환된 버전을 다음 요청에 사용한다. 충돌 시 화면의 내용을 유지하고 자동저장·게시를 중단한다. 사용자는 작성 내용을 복사해 보관한 뒤 최신 초안을 다시 열어 비교해야 한다. 최신 버전을 임의로 받아 자동 재저장하지 않는다.

API 계약이 바뀌므로 V8과 프론트·백엔드를 함께 반영해야 한다. 게시 요청의 초안 버전 검사 및 게시글 버전 관리는 별도의 후속 작업이다.

## 게시·수정 완료 버전 검사

V9은 `notes.content_version`과 `drafts.base_note_version`을 추가한다. 게시 요청은 `draftVersion`을 전달하며, 서버는 발행할 초안을 잠근 뒤 현재 버전을 비교한다. 완료된 초안의 같은 발행 재시도는 기존 게시글을 반환한다.

수정 요청은 `noteVersion`을 전달한다. 수정 초안에는 편집을 시작한 시점의 게시글 버전을 보관하며 초안을 다시 열어도 이 값을 유지한다. 서버는 게시글을 잠근 뒤 요청 버전과 초안의 기준 버전을 모두 검사한다. 갱신 시 내용 버전을 증가시키고 본문·태그·초안 완료 처리를 함께 커밋한다. 게시글 내용 버전은 JPA `@Version`이 아니라 기존 게시글 행 잠금 아래 명시적으로 증가시켜 조회수·좋아요 변경과 분리한다.

초안 저장·게시글 수정·초안 발행의 HTTP 409 응답은 에디터 내용을 유지하며 안내한다. V9 이전 수정 초안은 기준 버전을 알 수 없으므로 발행을 거절한다. 작성 내용을 보관한 뒤 최신 게시글을 열어 수정해야 한다. 기존 게시글은 내용 버전 0으로 초기화된다.

실제 MySQL 잠금 경쟁 및 트랜잭션 장애 검증은 아직 별도로 필요하다. 초안 없는 새 게시 요청의 멱등성 키 처리도 후속 과제다.

## 게시 요청 멱등성

POST /api/note는 Idempotency-Key 헤더가 필수다. V10의 publication_requests에 사용자·키·요청 해시·최초 응답을 저장한다. 게시글과 요청 결과는 같은 트랜잭션으로 저장한다. 사용자 행 잠금으로 같은 사용자의 게시 요청을 직렬화하며 사용자·키 유일성 제약으로 중복을 방어한다. 같은 키와 같은 내용은 최초 응답을 반환하고 다른 내용은 409로 거절한다.

브라우저는 사용자별 원본 요청과 키를 sessionStorage에 저장한다. 통신 실패·서버 오류 후에는 원본으로 재시도하며, 편집 내용이 바뀌었다면 이전 요청 결과를 확인할지 안내한다. 성공 또는 명확한 4xx 거절 시 지운다. 저장소가 차단되면 메모리 재시도만 지원한다. 서로 다른 탭에서 독립적으로 시작한 게시 요청은 서로 다른 의도로 취급한다.

V10·프론트·백엔드를 함께 적용하고 기존 API 호출자도 헤더를 추가해야 한다. CORS에서 이 헤더를 허용한다. 요청 기록은 현재 자동 만료하지 않는다. 사용자별 직렬화의 처리량, 보존 기간 및 정리 정책은 운영 후속 과제다. PUT 수정의 일반 멱등성 키는 이번 범위에 포함하지 않는다. 실제 DB 동시 요청·롤백·브라우저 통합 검증은 별도로 필요하다.

## 노트–태그 연결 보호

기존 V1 스키마와 NoteTag 엔티티에 (note_id, tag_id) 유일성 제약이 있어 중복 연결을 금지한다. V1의 태그 외래키에는 ON DELETE CASCADE가 없으므로 참조 중인 태그 삭제를 거절한다. 연결에는 Tag로의 JPA 삭제 cascade를 설정하지 않는다. 게시글에서 태그를 제거하면 연결만 삭제하며, 공유 태그 자체는 보존한다. 외래키 이름을 엔티티에도 명시했다. 현재 태그 자체를 삭제하는 API는 없다.

연결 저장이 실패하면 게시·수정 트랜잭션을 롤백한다. 기존 DB가 baseline 처리된 경우 실제 DB 제약이 V1과 일치하는지는 별도로 확인해야 한다. 이번 정리는 테스트 추가 및 실행 없이 수행했다.

## 스토리 소유권과 삭제

노트 게시·이동 및 초안 저장에서 스토리를 연결할 때 사용자 소유의 활성 스토리만 허용한다. 존재하지 않거나 타인 소유인 스토리는 404로 거절한다. 게시·수정·초안 저장·스토리 수정·삭제는 사용자 행을 먼저 잠그며, 같은 사용자 작업 사이의 연결·삭제 충돌을 직렬화한다. 스토리 대상 조회에도 쓰기 잠금을 사용한다.

일반 스토리 삭제는 소속된 활성 노트를 기본 스토리로 옮기고 미발행 초안의 storyId도 변경한 뒤 스토리를 소프트 삭제한다. 모두 같은 트랜잭션이다. 노트 내용 버전과 초안 버전을 증가시켜 이전 화면의 요청이 삭제된 소속을 되살리지 못하도록 한다. 수정 초안의 기존 게시글 기준 버전은 유지되므로 노트 이동 후 해당 초안을 발행하려면 최신 게시글과 비교해야 한다. 과거 잘못 연결된 타인 노트가 있으면 자동 이동하지 않고 삭제를 거절한다.

V11은 stories.is_default를 추가하고, 활성 기본 스토리를 사용자당 하나로 제한하는 generated-column 유일성 제약을 만든다. 기존 활성 '기본 폴더' 중 가장 오래된 것을 기본으로 지정하고 나머지는 일반 스토리로 보존한다. 기본 스토리는 삭제·이름 변경을 금지한다. 기본 스토리 생성도 사용자 잠금과 DB 제약으로 보호한다. 기존 중복 스토리를 임의로 합치거나 삭제하지 않는다.

프론트 삭제 안내를 기본 스토리 이동으로 수정하고 노트·초안 캐시도 무효화한다. V11·백엔드·프론트를 함께 반영해야 한다. 사용자 요청에 따라 테스트를 추가하거나 실행하지 않았으며 컴파일·타입 검사만 수행한다. 실제 DB 마이그레이션·동시 요청·삭제 복구 검증은 남아 있다.

## 작성·발행 체크리스트 마무리

태그 생성은 MySQL 업서트로 중복 이름을 오류 없이 재사용한다. 태그를 정렬된 순서로 처리한 뒤 잠금 조회(current read)로 ID를 확보하므로 REPEATABLE READ의 오래된 스냅샷에 의존하지 않는다. DB collation이 같은 태그로 취급하는 여러 이름은 ID로도 중복 제거해 연결한다. 데드락 가능성을 줄이지만 모든 잠금 실패를 자동 재시도하는 구현은 아니다. 실패하면 전체 게시가 롤백되고 동일 멱등성 키로 재시도할 수 있다.

태그 입력 정책은 NFKC 정규화, 앞뒤 공백 제거, 연속 공백 축약, Locale.ROOT 소문자화다. 노트당 최대 20개, 이름은 최대 30 코드포인트다. 기존 태그 표시 이름과 ID를 강제로 변경하거나 병합하지 않는다. 기존 DB의 case-insensitive collation으로 같은 이름을 재사용하며, 기존 태그의 전각 등 다른 표현을 모두 소급 병합하는 데이터 정리는 포함하지 않는다.

노트 삭제 시 미발행 수정 초안의 noteId와 baseNoteVersion을 비워 새 글 초안으로 보존한다. 제목·본문·태그를 지우지 않고 버전을 올려 오래된 편집 화면의 요청을 거절한다. 사용자 잠금 아래 삭제와 초안 보존을 같은 트랜잭션에서 수행한다.

스토리 태그는 별도 story-tag 저장 테이블이 아니라 노트의 실제 태그·소속에서 계산된다. 노트 게시·태그 수정·스토리 삭제 이동 시 콘텐츠 관련 캐시(스토리 상세/노트 목록/태그/검색/피드/추천/그래프)를 무효화한다. QueryProvider는 이전 데이터가 남아 있는 활성 쿼리의 갱신 실패를 알리고 해당 오류 쿼리의 재조회 버튼을 제공한다. 처음부터 데이터가 없는 조회 실패 화면은 각 화면의 오류 처리를 따른다.

체크리스트의 코드 대응은 반영했으나 실제 DB 제약 적용, 마이그레이션 실행, 동시 요청·트랜잭션 실패·브라우저 장애 검증은 완료하지 않았다. 사용자 요청대로 테스트를 추가·실행하지 않았으며 컴파일·타입 검사만 수행한다.

## 게시 재시도 흐름 변경 (이전 브라우저 방식 대체)

publicationAttempt.ts를 제거하고 publicationRecovery.ts로 대체했다. 이전 본문을 저장해 일반 게시 버튼에서 대신 전송하는 기능과 confirm 창은 제거했다. 신규 게시에서는 현재 내용을 캡처하고 같은 키·내용으로 최대 3회 시도한다. 통신 TypeError, HTTP 408/429/5xx만 재시도한다. 결과 불명 시 키와 비교용 fingerprint를 보관하며 작성 내용을 유지하고 임시저장을 일시 중단한다.

다음 신규 게시 전에 POST /api/note/publication/{key}/resolve로 이전 결과를 확인한다. 사용자 잠금을 게시와 공유하여 완료된 결과를 반환하거나 아직 반영되지 않은 키에 cancelled 기록을 저장한다. 취소된 키의 늦은 원 요청은 거절하므로 단순 조회에서 미발견된 요청을 새 키로 재게시하는 경쟁을 방지한다. 결과 확인 실패 시 기록을 유지하고 새 게시를 진행하지 않는다.

이전 요청이 완료됐으며 현재 내용과 같다면 완료 흐름으로 이동한다. 현재 내용이 달라졌다면 새 내용을 보존하고 이전 게시 성공을 안내하며 즉시 새로 게시하거나 초기화하지 않는다. 이전 요청이 취소됐으면 그 이후 현재 내용으로 새 요청을 보낸다. 서버 멱등성은 유지하며 새로운 DB 마이그레이션은 필요하지 않다. 클라이언트·서버 API를 함께 배포해야 한다. 테스트는 실행하지 않고 컴파일·타입 검사만 수행했다.

## 사용자 행 잠금 제거

현재 코드에는 사용자 행 쓰기 잠금이 없다. PublicationService는 사용자 존재를 일반 조회로 확인하고, 사용자·요청 키 유일성 제약 아래 pending/cancelled 처리 기록을 업서트한 뒤 해당 요청 행을 잠근다. publish와 resolve는 같은 요청 키 행으로 경쟁한다. pending 예약·노트 저장·완료 기록은 같은 트랜잭션이며 실패 시 예약도 롤백된다. 다른 요청 키는 사용자 잠금 때문에 기다리지 않는다. 기존 PublicationService 테스트의 제거된 메서드 참조와 저장소 mock만 갱신했으며 테스트는 실행하지 않았다.

스토리 연결 작업은 사용자 잠금 대신 대상 스토리를 잠근다. 노트 수정은 읽은 현재 소속과 이동 대상을 ID 순으로 잠근 뒤 초안·노트를 잠그고 소속 변화도 검사한다. 노트 삭제 역시 현재 스토리를 먼저 잠근다. 기본 스토리 생성은 기존 V11의 활성 기본 소유자 유일성 제약과 업서트로 보호한다. 같은 스토리의 작업 또는 기본 스토리에 대한 작업은 해당 스토리에서 대기할 수 있다. 서로 다른 사용자 행을 공통 잠금으로 사용하지 않는다. 공유 태그, 스토리 이동 등의 DB 잠금 대기·데드락 가능성 자체는 남으며 실패 시 트랜잭션을 롤백한다. 실제 동시 요청 검증은 남아 있다.

기존 마이그레이션을 적용한 환경에는 추가 스키마 변경이 필요하지 않다. compileJava만 검증하고 테스트는 실행하지 않는다.
