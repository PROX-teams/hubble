# 검색 기능 실제 DB 검증 및 성능 측정

측정일: 2026-10-05. 운영 DB 대신 별도로 생성한 일회용 MySQL을 사용했다.

## 1. 결론

**제목·본문 검색 일부 조건에서는 FULLTEXT가 빨랐지만, 스토리 검색 전체는 개선됐다고 결론 낼 수 없다.** 소속 노트를 검사하는 FULLTEXT 조건이 느렸고, 흔한 검색어에서 스토리 후보 누락도 확인됐다.

- JUnit 14개 실행: 실패·오류·건너뜀 0개. 기능 통합 검사 10개, 성능 측정 1개, 서비스 단위 검사 2개, 기존 데이터 마이그레이션 검사 1개.
- HTTP 180회: 모두 성공 응답. 성공 여부와 응답 구조 검사이며 모든 요청의 후보 완전성 검증은 아니다.
- 후보 집합 비교 15개 중 14개 동일, 1개 불일치. 불일치는 측정 데이터로 기록하는 방식이므로 JUnit 성공이 검색 전체의 정확성을 보증하지 않는다.

## 2. 환경과 데이터

- MySQL 8.0.45, ngram_token_size=2, utf8mb4_unicode_ci. 컨테이너 CPU 2개·메모리 1536 MiB 제한.
- 노트 20,001개, 스토리 1,001개, 태그 2,001개. 합성 데이터와 검사 기본 행을 포함한다.
- 합성 노트 본문: 최소 375자, 평균 1,049.8자, 최대 11,613자.
- SQL: 조건별 준비 실행 3회, 측정 20회. FULLTEXT/LIKE 실행 순서를 교대했다. JDBC 호출 시간으로 네트워크·연결 확보 비용도 포함한다.
- 두 방식 모두 같은 필드와 삭제 조건을 사용했고 후보 ID 집합을 비교했다. 캐시가 준비된 상태의 측정이다.

## 3. 기능 검증 및 수정

실제 V1~V6 마이그레이션, FULLTEXT 인덱스 4개, 제목 우선순위, 본문만 일치하는 노트와 부모 스토리, 태그·작성자 일치, 삭제 제외, 한 글자·기호 LIKE, 복수 단어 구문 검색, 스토리·노트 13개를 10개와 3개로 나눠 받기, HTTP 응답 및 종료된 목록 생략을 검사했다. 기존 데이터 검사는 소속 없는 노트와 삭제된 노트의 기본 스토리 보정 및 기존 소속 보존을 확인했다.

테스트 중 발견해 수정한 오류:

1. V6에서 외래 키가 있는 story_id를 바로 NOT NULL로 변경하면 MySQL이 거부했다. 기존 외래 키를 제거하고 컬럼 변경과 새 이름의 외래 키 생성을 함께 수행하도록 수정했다.
2. FULLTEXT 결과 ID를 수정 불가능한 리스트로 만들고 11번째 결과를 제거해 예외가 발생했다. 스토리와 노트 모두 수정 가능한 ArrayList를 사용하도록 고쳤다. 13개 결과의 페이지 회귀 검사로 확인했다.

노트 제목·본문의 `트랜잭션` 조건은 약 12.3배 빨랐다. 그러나 대부분의 본문에 포함된 `일반기록`은 LIKE가 더 빨랐다. FULLTEXT 적용만으로 모든 검색어가 빨라지는 것은 아니다.

실행 계획에서 제목·본문 단독 FULLTEXT는 ft_notes_title_content 인덱스 검색, LIKE는 노트 테이블 전체 스캔을 사용했다. 작성자·태그·소속 노트를 OR로 묶은 조건은 이 단독 검색과 다른 실행 계획을 갖는다. 스토리 상관 서브쿼리에서 FULLTEXT initialization 상태가 반복 관찰됐다.

## 5. 실제 통합 검색 API

`/api/search?keyword=...&page=...&size=10` 호출. 태그·스토리·노트 조회 및 응답 변환을 포함한다. 검색어 6종(트랜잭션, 희귀주제, 없는검색어, 자바 트랜잭션, C++, 자), 페이지 0·1을 고정 순서로 조합했다. 각 동시 요청 조건에서 준비 요청 5회 후 60회 측정했다.

| 동시 요청 수 | 요청 수 | 중앙값(ms) | p95(ms) | 처리량(요청/초) | HTTP 오류 |
|---:|---:|---:|---:|---:|---:|
| 1 | 60 | 581.97 | 2342.09 | 1.27 | 0 |
| 5 | 60 | 1443.82 | 9950.49 | 1.77 | 0 |
| 10 | 60 | 5314.60 | 30461.97 | 1.16 | 0 |

동시 요청 10개에서 p95가 약 30.46초였다. DB CPU가 제한된 이 환경에서 동시 요청을 늘려도 처리량이 늘지 않았다. 운영 환경의 처리량 수치로 일반화할 수는 없지만, 현재 검색 경로의 병목을 조사할 근거다. 이전 API는 측정하지 않았으므로 API 전후 개선율은 없다.

## 6. 후보 불일치: 미해결 사항

`일반기록` 스토리 조건에서 FULLTEXT 926개, LIKE 1,000개였다. 측정 후 별도 진단에서 같은 검색어로 노트를 독립적으로 FULLTEXT 조회한 소속 스토리는 1000개였다. 상관 스토리 조건 대비 74개가 빠졌다.

예: 스토리 3번에는 노트 2번이 있으며 본문은 `일반기록 개발 경험...`으로 시작한다. 노트를 독립 조회하면 FULLTEXT 점수가 0보다 크지만, 해당 스토리 후보 쿼리에서는 누락됐다. 따라서 단순히 LIKE와 FULLTEXT의 일반적인 의미 차이라고 설명할 수 없다.

**상관 서브쿼리와 FULLTEXT를 함께 사용한 현재 후보 조회 구조를 우선 조사해야 한다. 근본 원인은 아직 확정하지 않았고 이 누락은 수정하지 않았다.** 후보 집합을 각각 구한 뒤 합치는 쿼리 구조를 검토하고, 동일 데이터에서 후보·순위·실행 계획·API 성능을 다시 비교하는 것이 다음 작업이다.

## 8. 측정의 한계

합성 데이터, 단일 로컬 환경, 준비된 캐시, SQL 20회·HTTP 60회의 초기 측정이다. 부하 생성기는 요청이 끝나면 다음 요청을 보내는 방식이며 서버·DB·클라이언트가 호스트 자원을 공유한다. 검색어마다 페이지가 고정 배정되어 모든 조합을 측정한 것은 아니다. 로그인 사용자 상태, 프론트 캐시·입력 대기, 운영 데이터 분포, cold cache, CPU·디스크 지표, 인덱스의 쓰기 비용, 실사용 관련도 품질은 검증 범위 밖이다. 특히 소표본 p99는 일반화하지 않는다.
