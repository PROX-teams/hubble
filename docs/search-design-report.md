# 스토리·노트·태그의 데이터 특성에 따른 검색 설계 보고서

작성일: 2026-10-04

## 1. 목적과 확인 범위

이 보고서는 Hubble의 검색 화면에서 사용하는 `GET /api/search`를 대상으로 한다. 스토리·노트·태그의 실제 테이블 구조가 검색 대상, 후보 조회 방식, 결과 정렬 방식에 어떻게 연결되는지 설명한다.

근거는 현재 저장소의 엔티티, SQL 마이그레이션, 검색 저장소 및 서비스 코드다. 사용자 검색 기록을 근거로 한 보고서는 아니다. 2026-10-05 실제 DB 검증과 합성 데이터 성능 측정 결과는 [검색 실측 보고서](/Users/bum/Desktop/hubble-client/docs/search-benchmark-report.md)에 별도로 정리했다. 아래의 설계 이유는 현재 코드와 제품 요구를 연결한 판단이며, 실제 검색 품질을 입증한 결과와 구분한다.

## 2. 데이터 관계와 설계의 출발점

```text
users ── stories ── notes ── note_tags ── tags
  └──────────────── notes
```

| 대상 | 실제 데이터 특성 | 검색에 미치는 영향 |
|---|---|---|
| 스토리 | 작성자가 만든 노트 묶음. 필수 제목과 선택 설명을 가진다. | 묶음의 이름을 찾는 검색과, 묶음 안의 내용을 통해 찾는 검색을 지원한다. |
| 노트 | 필수 제목·본문을 가진 콘텐츠. 스토리에 소속되고 여러 태그를 가진다. | 제목 외에도 본문·태그·작성자를 통해 콘텐츠를 발견할 수 있어야 한다. |
| 태그 | 이름이 유일한 공유 분류 항목. 본문이나 작성자가 없다. | 이름 일치 수준과 실제 사용 빈도를 중심으로 정렬한다. |

스토리와 노트는 각각 `user_id`로 작성자를 참조한다. 노트와 태그는 다대다 관계이며, `note_tags`가 이를 연결한다. 스토리에 직접 연결되는 태그 테이블은 없다.

스토리와 노트에는 소프트 삭제 시각이 있다. 검색은 삭제되지 않은 콘텐츠를 대상으로 한다. 네이티브 FULLTEXT 검색에서는 콘텐츠와 작성자의 삭제 여부를 명시적으로 확인한다.

## 3. 스토리: 묶음의 이름과 내부 콘텐츠로 발견하도록 설계

### 3.1 테이블에서 확인한 특성

`stories`의 핵심 컬럼은 다음과 같다.

| 컬럼 | 제약·역할 |
|---|---|
| `id` | 기본 키 |
| `title` | 필수, 최대 100자 |
| `description` | 선택, TEXT |
| `user_id` | 필수 작성자 참조 |
| `category` | 필수 카테고리 |
| `icon` | 표현용 아이콘 |
| `view_count`, `like_count`, `bookmark_count` | 반응 집계 |
| `created_at`, `updated_at`, `deleted_at` | 생성·수정·삭제 시각 |

스토리는 자체적인 긴 본문을 가진 콘텐츠라기보다, 노트들이 소속되는 묶음이다. 설명은 생략할 수 있으므로 스토리 자체의 텍스트만으로 묶음 안의 모든 주제를 표현한다고 볼 수 없다.

### 3.2 특성과 연결한 검색 범위

현재 스토리 검색은 다음 조건 중 하나를 만족하면 후보로 포함한다.

1. 스토리 제목 또는 설명에서 검색어가 발견된다.
2. 스토리 작성자 닉네임에서 검색어가 발견된다.
3. 소속 노트의 제목 또는 본문에서 검색어가 발견된다.

예를 들어 제목이 `백엔드 공부`인 스토리 안에 `트랜잭션 정리`라는 노트가 있으면, `트랜잭션` 검색으로 노트와 해당 스토리를 각각 찾을 수 있도록 구현했다. 사용자가 묶음 이름을 기억하지 않아도 내부 내용을 통해 발견할 수 있게 하기 위한 선택이다.

현재는 소속 노트의 태그나 작성자 이름까지 스토리 후보 조건으로 확장하지 않았다. 따라서 노트에 붙은 태그에만 검색어가 있고 노트 제목·본문에는 없으면, 그 조건만으로 스토리가 검색되지는 않는다.

### 3.3 후보 조회 방식과 이유

지원되는 검색어는 스토리의 `(title, description)` FULLTEXT 검색과 소속 노트의 `(title, content)` FULLTEXT 검색을 사용한다. 작성자 닉네임도 별도 FULLTEXT 검색 조건에 포함한다. 한 글자나 기호가 포함된 입력은 LIKE 포함 검색으로 처리한다.

스토리 자체에 FULLTEXT를 사용하는 이유는 제목과 설명의 텍스트를 검색하고 점수를 활용하기 위해서다. 다만 설명이 선택 항목이라는 점에서, 스토리만 놓고 볼 때 FULLTEXT가 반드시 필요하다고 단정하지 않는다. 소속 노트의 본문까지 검색 범위를 넓힌 현재 구조에서는 노트의 텍스트 검색이 추가적인 적용 근거가 된다.

소속 노트 검색에는 `EXISTS`를 사용한다. 필요한 판단은 “일치하는 노트가 하나라도 있는가”이기 때문이다. 같은 스토리의 여러 노트가 일치해도 스토리 결과는 한 행으로 유지하며, 검색을 위해 소속 노트 전체를 응답으로 가져오지 않는다. 이 방식이 실제로 더 빠른지는 실행 계획과 측정으로 확인해야 한다.

### 3.4 정렬 방식과 이유

스토리 제목의 정확 일치 → 접두어 일치 → 포함 일치 → 그 밖의 후보 순으로 우선순위를 정한다. 같은 제목 우선순위에서는 스토리 제목·설명의 FULLTEXT 점수, 생성 시각, ID를 차례로 비교한다. LIKE 경로에서는 FULLTEXT 점수 없이 생성 시각과 ID를 비교한다.

묶음을 찾는 검색에서 이름이 직접 맞는 스토리를 먼저 보여주려는 설계다. 따라서 스토리 제목이 `트랜잭션`인 결과는 내부 노트에만 `트랜잭션`이 있는 `백엔드 공부` 스토리보다 우선한다.

주의할 점은 소속 노트의 검색 점수나 일치 노트 개수를 스토리 순위에 반영하지 않는다는 것이다. 노트 일치는 현재 스토리를 후보에 포함하는 조건이다. 내부 내용의 관련도까지 계산한 스토리 순위는 아직 아니다.

## 4. 노트: 실제 내용을 찾는 문서 검색으로 설계

### 4.1 테이블에서 확인한 특성

| 컬럼 | 제약·역할 |
|---|---|
| `title` | 필수, 최대 100자 |
| `content` | 필수, TEXT |
| `user_id` | 필수 작성자 참조 |
| `story_id` | 필수 소속으로 변경한 참조. DB 제약 적용은 마이그레이션 필요 |
| `category`, `image_url` | 분류와 표현 정보 |
| 반응 집계 컬럼 | 조회수·좋아요·북마크 수 |
| `popularity_score` | 북마크 수 × 5 + 좋아요 수 × 3 + 조회수 / 10의 정수 몫 |
| 생성·수정·삭제 시각 | 콘텐츠 생명주기 |

본문이 필수이므로 노트는 텍스트 내용을 직접 검색할 수 있는 콘텐츠 단위다. TEXT 컬럼이라는 사실만으로 실제 본문이 길다는 통계가 입증되는 것은 아니지만, 제목보다 많은 정보를 담을 수 있는 구조다.

노트는 스토리에 반드시 속한다는 제품 요구를 반영했다. 생성 시 소속을 생략하면 기본 스토리에 넣고, 수정 시 생략하면 기존 소속을 유지한다. 기존 소속이 없는 데이터는 기본 스토리로 보정하도록 마이그레이션을 작성했다.

### 4.2 특성과 연결한 검색 범위

노트 제목·본문·작성자 닉네임·태그 이름 중 하나에서 일치하면 후보가 된다. 사용자가 노트 제목을 모르더라도 본문 주제, 분류 태그 또는 작성자를 알고 있을 수 있기 때문이다.

노트 검색 조건에는 소속 스토리의 제목·설명이 포함되지 않는다. 예를 들어 `백엔드 공부` 스토리에 속했다는 이유만으로 내용과 무관한 모든 노트가 `백엔드 공부` 검색 결과에 포함되지는 않는다.

### 4.3 후보 조회 방식과 이유

지원되는 입력에는 `(title, content)` FULLTEXT ngram 검색을 사용한다. 본문까지 검색해야 하므로 제목의 단순 비교보다 텍스트 검색 인덱스를 사용할 근거가 명확하다. 이는 본문 검색을 처리하려는 선택이며, 합성 데이터 실측에서는 검색어와 조회 범위에 따라 FULLTEXT가 빠르거나 느렸다. 전체 API의 전후 개선율은 측정하지 않았다.

태그로 노트를 찾을 때는 `note_tags`를 통해 연결된 `tags.name`을 확인한다. FULLTEXT 경로의 태그 조건은 `EXISTS`로 구현했다. 하나의 노트에 여러 일치 태그가 있어도 해당 노트를 한 번만 반환하기 위한 구조다.

### 4.4 정렬 방식과 이유

노트도 제목 정확 일치 → 접두어 일치 → 포함 일치 → 그 밖의 후보 순으로 정렬한다. 같은 제목 우선순위에서는 제목·본문을 합친 FULLTEXT 점수, 생성 시각, ID를 비교한다. LIKE 경로에서는 제목 우선순위 다음에 생성 시각과 ID를 비교한다.

제목이 콘텐츠의 주제를 대표한다는 가정 아래 제목의 직접 일치를 우선한다. 동일한 제목 우선순위 안에서 본문 검색 점수를 활용해 텍스트가 맞는 정도를 추가로 비교한다.

인기도는 키워드 검색 정렬에서 제외했다. 검색어와 직접 맞는 콘텐츠가 인기 콘텐츠보다 앞에 나타나도록 하고, 조회수·좋아요·북마크 변화가 스크롤 중 결과 순서를 바꾸는 원인을 줄이기 위한 선택이다. 검색어가 없는 인기 목록은 여전히 인기도를 사용한다.

태그·작성자 이름의 정확 일치 여부에는 별도 순위 규칙이 없다. 예를 들어 `자바` 검색에서 태그가 정확히 `자바`인 노트와 `자바스크립트`인 노트가 모두 후보가 되더라도, 태그의 정확 일치만으로 전자를 먼저 보여주지는 않는다. 제목·본문 점수와 생성 시각이 순서를 결정한다. 이 부분은 현재 관련도 설계의 한계다.

## 5. 태그: 공유된 분류 이름을 찾는 검색으로 설계

### 5.1 테이블에서 확인한 특성

`tags`는 `id`와 최대 30자의 필수 `name`으로 구성된다. 이름에는 UNIQUE 제약이 있다. 태그에는 본문·작성자·카테고리·사용 횟수 컬럼이 없다.

같은 태그 레코드를 여러 노트가 공유한다. `note_tags`에는 `id`, `note_id`, `tag_id`가 있으며, `(note_id, tag_id)`의 UNIQUE 제약으로 같은 노트에 같은 태그가 중복 연결되지 않도록 한다.

태그의 사용 빈도는 태그 행에 저장된 값을 읽는 방식이 아니다. 삭제되지 않은 노트와 연결된 `note_tags` 행 수를 집계한다. 이는 조회수나 클릭수가 아니라 해당 태그가 연결된 노트의 수를 나타낸다.

### 5.2 태그 목록의 검색 방식과 이유

통합 검색에 별도로 표시하는 태그 목록은 `name LIKE '%검색어%'` 조건을 사용한다. 짧은 분류 이름의 일부를 입력해 관련 이름을 찾는 동작을 제공하기 위해서다.

현재 태그 검색은 등록된 모든 이름의 사전 조회가 아니다. 삭제되지 않은 노트에 실제로 연결된 태그를 찾는다. 사용 중인 노트가 없는 태그는 목록에서 제외된다. 선택 후 탐색할 콘텐츠가 있는 분류를 노출하는 구조다.

이름 정확 일치 → 접두어 일치 → 포함 일치 순으로 정렬하고, 같은 수준에서는 사용 빈도 내림차순과 이름 오름차순을 적용한다. 정확한 이름을 먼저 찾게 하고, 동률 후보에서는 더 많이 사용되는 분류를 먼저 보여주려는 선택이다.

태그 이름이 짧다는 사실은 LIKE의 성능을 보장하지 않는다. 특히 앞에 `%`가 있는 포함 검색과 실시간 사용 빈도 집계는 태그·연결 데이터 증가에 따라 비용이 커질 수 있다. 최대 10개 응답이라는 제한도 전체 조회·집계 비용을 10개 수준으로 제한한다는 뜻은 아니다.

### 5.3 태그 목록과 태그를 통한 노트 검색의 차이

| 사용처 | 반환 대상 | 후보 조회 방식 | 순위 기준 |
|---|---|---|---|
| 검색 화면의 태그 목록 | 태그 이름 | LIKE 포함 검색 | 이름 일치 수준 → 사용 빈도 → 이름 |
| 태그를 통해 노트 찾기 | 노트 | FULLTEXT 경로에서는 태그 FULLTEXT, 보완 경로에서는 포함 검색 | 노트 제목 우선순위 → 노트 텍스트 점수 → 최신순 |

태그 목록은 이름 자체를 찾는 기능이고, 노트 검색의 태그 조건은 그 이름이 연결된 콘텐츠를 찾는 기능이다. 따라서 현재 두 사용처의 후보 조회와 정렬 규칙이 다르다. 기호를 포함한 이름과 짧은 입력에서 두 경로의 결과가 일관적인지는 별도로 검증해야 한다.

## 6. 공통 요청 처리와 조회 설계

### 검색어에 따른 경로 선택

검색어 앞뒤 공백을 제거한 후, 공백으로 구분된 모든 단어가 두 글자 이상의 문자·숫자로만 구성되면 FULLTEXT를 사용한다. 그 밖의 입력은 LIKE 포함 검색으로 처리한다. 예를 들어 `트랜잭션`은 FULLTEXT 경로이며 `C++`나 한 글자 입력은 LIKE 경로다.

FULLTEXT 인덱스 마이그레이션은 ngram 파서를 지정한다. 코드의 두 글자 조건은 기본 2글자 토큰 설정을 전제로 한다. 실제 DB 설정이 이에 맞는지 확인해야 한다. FULLTEXT 질의는 입력을 따옴표로 감싼 구문 형태로 전달하므로, 공백으로 나뉜 단어를 독립적인 OR 조건으로 검색하는 구현은 아니다.

### 정렬 후 필요한 구간만 조회

필터와 정렬은 DB 쿼리에서 수행한 뒤 `LIMIT`과 `OFFSET`을 적용한다. 모든 후보를 애플리케이션으로 가져와 정렬한 후 10개를 자르는 구조가 아니다.

FULLTEXT 경로는 먼저 정렬된 콘텐츠 ID를 조회하고, 이후 필요한 엔티티와 작성자를 조회한다. 두 번째 조회 결과를 첫 ID 목록 순서로 다시 조립해 검색 순서를 유지한다.

### 결과 종류별 무한스크롤

스토리와 노트는 각각 별도로 정렬하고 페이지를 조회한다. `page=0&size=10`이면 스토리 최대 10개와 노트 최대 10개를 반환한다. 둘을 합쳐 10개를 반환하는 구조가 아니다.

각 목록은 최대 11개를 조회해 다음 결과 유무를 판단하는 Slice를 사용한다. 전체 결과 개수를 계산하는 COUNT 조회는 하지 않는다. 검색 결과의 총 개수보다 다음 묶음 존재 여부가 필요한 화면에 맞춘 선택이다. 단, 스토리 카드에 표시할 소속 노트 개수는 별도로 일괄 집계한다.

태그 목록은 첫 페이지에서 최대 10개만 제공한다. 이후 스크롤은 스토리·노트의 결과를 확장하며, 종료된 종류는 추가 조회를 생략한다. 프론트엔드는 누적 결과의 중복 ID를 제거한다.

### 검색 전용 응답

스토리 검색 응답은 ID·제목·작성자·소속 노트 개수로 구성한다. 사용자의 좋아요·북마크 여부를 덧붙이는 조회는 하지 않는다. 검색 화면에서 사용하는 정보를 중심으로 응답을 구성한 선택이다.

미사용 스토리 단독 키워드 검색을 목록 API에서 제거했다. `/api/story`는 목록·카테고리 조회를 담당하고, 검색창은 `/api/search`를 호출한다. 이 보고서는 다른 목록 API의 개별 필터 기능까지 하나의 검색 API로 통합했다고 주장하지 않는다.

## 7. 검증 상태와 남은 한계

| 항목 | 확인 상태 |
|---|---|
| 소속 노트 제목·본문을 통한 스토리 검색 | 기본 사례 통과. 합성 데이터의 흔한 검색어에서 후보 누락 발견, 미해결 |
| 수정 시 기존 스토리 소속 유지 | 회귀 테스트 통과 |
| 소속 없는 기존 노트의 수정 시 기본 스토리 배치 | 회귀 테스트 통과 |
| 노트 서비스 테스트 | 총 6개, 실패·오류 0개 |
| FULLTEXT 인덱스 및 노트 소속 필수 제약 | 일회용 MySQL 8.0.45에 V1~V6 적용 및 기존 NULL 데이터 보정 검사 통과. 운영 DB 적용은 별도 |
| FULLTEXT SQL·마이그레이션의 실제 DB 동작 | 검색 관련 JUnit 14개 통과. 후보 집합 비교는 15조건 중 1조건 불일치 |
| 검색 지연 시간·실행 계획·관련도 품질 | SQL 및 API 합성 데이터 실측 완료. 실사용 관련도 품질 미검증 |

키워드 검색에서 인기도를 제외하고 ID를 동률 정렬 기준으로 추가했지만, offset 페이지네이션의 중복·누락 가능성을 모두 해결한 것은 아니다. 조회 사이에 일치 콘텐츠가 추가·삭제되거나 검색 대상 텍스트가 수정되면 페이지 경계가 달라질 수 있다. 프론트엔드의 중복 제거는 누락을 복구하지 않는다.

노트의 `story_id NOT NULL`과 외래 키는 소속 참조가 존재하도록 한다. 다만 스토리를 소프트 삭제했을 때 소속 노트를 어떻게 처리할지는 별도 정책이다. 이번 수정으로 삭제된 스토리에 소속된 노트의 처리까지 해결했다고 볼 수는 없다.

제목·본문·태그·작성자·소속 노트 일치와 한 글자·기호·복수 단어 입력의 기본 사례는 검사했다. 다만 흔한 검색어의 스토리 후보 누락과 소속 노트 FULLTEXT 조회 병목이 발견돼 우선 개선이 필요하다. 운영 분포의 결과 품질은 별도 검증해야 한다.
