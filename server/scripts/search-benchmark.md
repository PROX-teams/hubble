# 로컬 MySQL 검색 검증·측정

## 실행

Docker, Java 17, Gradle 의존성을 내려받을 네트워크가 필요하다.

저장소 루트에서 다음을 실행한다.

```bash
bash server/scripts/search-local-benchmark.sh
```

노트 수를 바꾸려면 다음과 같이 실행한다.

```bash
SEARCH_BENCHMARK_NOTES=50000 bash server/scripts/search-local-benchmark.sh
```

스크립트는 `hubble-search-benchmark` 일회용 MySQL 컨테이너를 생성하고 종료 시 제거한다.
기존 이름의 컨테이너가 있으면 덮어쓰지 않고 중단한다. 기존 서비스 DB나 `.env`의 접속 정보를 사용하지 않는다.
DB 이름은 `hubble_search_benchmark`, 포트는 루프백 주소의 `13316`이다. 테스트용 자격 증명만 사용한다.

테스트는 환경변수 `SEARCH_MYSQL_TESTS=true`일 때만 실행한다.
시간 측정은 추가로 `SEARCH_BENCHMARK=true`일 때만 실행한다. 일반 테스트 실행에는 합성 데이터 생성이나 성능 측정이 포함되지 않는다.
스크립트는 환경변수 변경에도 테스트가 다시 실행되도록 Gradle의 `--rerun-tasks`를 사용한다.

## 검증 범위

- 실제 V1~V6 마이그레이션, FULLTEXT 인덱스 및 ngram 설정
- 제목 정확·접두어·포함 일치와 본문 일치의 순위
- 본문만 일치하는 노트 및 해당 스토리의 검색
- 태그·작성자만 일치하는 검색
- 삭제된 노트·작성자의 제외
- 한 글자와 기호 입력의 LIKE 경로
- 여러 단어 입력의 구문 검색
- 스토리·노트 10개 초과 시 페이지 처리와 다음 페이지 유무
- 실제 HTTP 응답, 노트 태그 로딩과 본문 요약
- 다음 페이지의 태그·종료된 종류 생략
- V5까지의 기존 데이터에서 소속 없는 노트를 보정하는 V6 마이그레이션

## 성능 비교의 의미

SQL 비교는 아래 세 검색 범위에서 후보를 찾는 `COUNT(*)` 쿼리를 비교한다.

1. 노트 제목·본문
2. 노트 제목·본문·작성자·태그
3. 스토리 제목·설명·작성자·소속 노트 제목과 본문

LIKE와 FULLTEXT를 제외한 검색 범위를 맞추고, 후보 ID 집합이 같은지 기록한다.
검색어는 결과가 많은 경우·적은 경우·없는 경우 및 복수 단어를 포함한다.
각 쿼리 3회 준비 실행 후 20회 측정하며 두 방식의 실행 순서를 번갈아 바꾼다.
측정 시간은 애플리케이션에서 JDBC 호출 완료까지의 시간으로 네트워크와 DB 연결 확보 비용을 포함한다.

이 SQL 비교에는 실제 검색 API의 제목 그룹·점수 정렬, LIMIT/OFFSET, 엔티티 재조회 및 DTO 변환이 없다.
따라서 이 결과를 그대로 API 전체의 성능 개선율이나 실제 페이지 쿼리의 개선율로 해석하면 안 된다.
EXPLAIN ANALYZE는 비교 쿼리의 접근 방식을 설명하기 위한 자료다.
지원되지 않으면 오류와 일반 EXPLAIN 결과를 함께 기록한다.

HTTP 측정은 테스트 환경의 실제 `/api/search`를 호출한다.
동시 요청 수 1·5·10에서 각각 60회 요청하며, 검색어 6종과 페이지 0·1을 조합한다.
응답 성공 상태와 통합 응답 구조를 확인한다.
검색어별로 페이지가 번갈아 배정되는 고정 workload이므로 모든 검색어의 모든 페이지 조합을 측정한 것은 아니다.
측정 클라이언트는 최대 동시 요청 수를 유지하면서 완료 후 다음 작업을 실행하는 closed-loop 방식이다.
프론트엔드 캐시와 300ms 입력 대기는 측정에 포함하지 않는다.
현재 API만 측정하므로 이전 API 대비 개선율을 주장할 수 없다.

## 결과와 제한

- 원본 수치·실행 계획: `server/api/build/reports/search-benchmark/results.json`
- JUnit 결과: `server/api/build/test-results/test/`
- HTML 테스트 보고서: `server/api/build/reports/tests/test/index.html`
- 정리된 실측 보고서: [검색 실측 보고서](/Users/bum/Desktop/hubble-client/docs/search-benchmark-report.md)

데이터는 합성 데이터이고 MySQL 컨테이너는 CPU 2개, 메모리 1536 MiB로 제한한다.
본문 길이 및 행 수는 원본 JSON에 기록한다. 서버와 부하 클라이언트, DB는 같은 호스트 자원을 공유한다.
캐시가 준비된 상태를 측정하며 cold-cache 실험은 하지 않는다.
20회 SQL 측정·60회 HTTP 측정은 초기 비교이며, 특히 p99는 표본이 작아 일반화할 수 없다.
CPU·디스크·운영 부하·인덱스 추가에 따른 쓰기 비용은 이 실험에서 측정하지 않는다.
한 번의 로컬 실험으로 운영 환경의 처리량이나 보장 응답 시간을 확정하지 않는다.
